# Reflection

I drew the tool boundaries around observable intent and side effects. `search_catalog` answers a question without changing state. `save_reading_item` persists one known catalog book, with a database uniqueness constraint making retries safe. `plan_reading` represents one higher-level intent: adding a matching book to a reading list. It composes the same search and save implementations used by the individual tools rather than duplicating their logic. Although the workflow contains two steps, its purpose is cohesive and its return value states the selection rule and save outcome. I chose alphabetical ordering to keep behavior explainable; this is a reproducible policy, not a claim that the selected book is academically best.

Three tools feel appropriate for this deliberately narrow workflow because they expose observation, mutation, and composition separately. The constraint would become restrictive for a complete library assistant, where borrowing, removing saved items, and listing saved books deserve distinct interfaces. The main design challenges were preventing implicit writes during lookup, distinguishing an empty search from an unsuccessful workflow, and avoiding duplicate entries when a model retries. Typed schemas, explicit errors, and transactional SQLite storage address these issues. Next steps would be connecting an authorized real catalog, adding relevance ranking with an explicit policy, and evaluating natural-language tool selection across a larger prompt set. The no-key protocol demonstration validates transport and tool behavior, while the completed live OpenAI run demonstrates tool selection and error reporting for the six example requests.
